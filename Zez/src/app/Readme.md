# Device and call table
```sql


BEGIN;

-- 1. Drop the existing tables
DROP TABLE IF EXISTS public.call_logs CASCADE;
DROP TABLE IF EXISTS public.device_call_logs CASCADE;
DROP TABLE IF EXISTS public.calls CASCADE;
DROP TABLE IF EXISTS public.callss CASCADE;
DROP TABLE IF EXISTS public.devicess CASCADE;
DROP TABLE IF EXISTS public.devices CASCADE;

-- 2. Create the devices table
CREATE TABLE public.devices (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    -- New identifiers
    device_id TEXT UNIQUE,
    persistentid TEXT UNIQUE,
    androidid TEXT UNIQUE,

    -- Device information
    device_name TEXT,
    device_model TEXT,
    manufacturer TEXT,
    brand TEXT,
    platform TEXT NOT NULL DEFAULT 'Android',
    os_version TEXT,
    app_version TEXT,

    -- SIM information
    sim1_phone_number TEXT,
    sim2_phone_number TEXT,
    sim1_carrier TEXT,
    sim2_carrier TEXT,
    sim1_country_iso TEXT,
    sim2_country_iso TEXT,
    primary_phone_number TEXT,

    -- Authentication
    token_hash TEXT UNIQUE NOT NULL,

    device_details JSONB NOT NULL DEFAULT '{}'::JSONB,

    registration_status TEXT NOT NULL DEFAULT 'active'
        CHECK (registration_status IN ('active', 'revoked')),

    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    last_seen_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 3. Create indexes for devices
CREATE INDEX devices_primary_phone_number_idx
    ON public.devices (primary_phone_number);

CREATE INDEX devices_created_at_idx
    ON public.devices (created_at);

-- 4. Create the call_logs table
CREATE TABLE public.call_logs (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,

    device_id UUID NOT NULL
        REFERENCES public.devices(id)
        ON DELETE CASCADE,

    external_id_hash TEXT NOT NULL,
    call_timestamp TIMESTAMPTZ,
    encrypted_payload TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT call_logs_device_external_id_unique
        UNIQUE (device_id, external_id_hash)
);

-- 5. Create indexes for call logs
CREATE INDEX call_logs_device_timestamp_idx
    ON public.call_logs (device_id, call_timestamp DESC);

CREATE INDEX call_logs_created_at_idx
    ON public.call_logs (created_at DESC);

COMMIT;


```

device_id	Which registered phone owns the call

# Zez — Devices Database Schema

## 1. Overview

The `devices` table stores information about each mobile app installation registered with the Zez backend.

Each registered installation receives a unique UUID generated by PostgreSQL. The device record stores optional hardware, operating-system, SIM-card, and phone-number details, together with the authentication token hash and registration timestamps.

The `devices` table is shared by all installations. A separate table is not created for each phone.

### Main objectives

- Identify each registered Zez installation.
- Associate uploaded call logs and other records with their originating device.
- Store optional SIM 1 and SIM 2 information.
- Keep track of device registration and recent activity.
- Authenticate devices without using phone numbers as credentials.
- Support devices that have no SIM card or whose SIM numbers cannot be retrieved.

## 2. Table definition

Table name: `public.devices`

| Field | Data type | Required? | Purpose |
|---|---|---|---|
| `id` | UUID | Yes | Unique identifier for the registered device installation. Primary key. |
| `device_name` | TEXT | No | Human-readable device name, if available. |
| `device_model` | TEXT | No | Model name reported by the operating system. |
| `manufacturer` | TEXT | No | Manufacturer, such as Samsung or Vivo. |
| `brand` | TEXT | No | Device brand reported by Android. |
| `platform` | TEXT | Yes | Operating-system platform. Defaults to `Android`. |
| `os_version` | TEXT | No | Android version reported by the device. |
| `app_version` | TEXT | No | Installed Zez app version. |
| `sim1_phone_number` | TEXT | No | Phone number associated with SIM slot 1, if available. |
| `sim2_phone_number` | TEXT | No | Phone number associated with SIM slot 2, if available. |
| `sim1_carrier` | TEXT | No | Mobile network operator associated with SIM 1, if available. |
| `sim2_carrier` | TEXT | No | Mobile network operator associated with SIM 2, if available. |
| `sim1_country_iso` | TEXT | No | Country ISO code associated with SIM 1, if available. |
| `sim2_country_iso` | TEXT | No | Country ISO code associated with SIM 2, if available. |
| `primary_phone_number` | TEXT | No | Preferred phone number for display or contact purposes. |
| `token_hash` | TEXT | Yes | SHA-256 hash of the device's secret authentication token. Must be unique. |
| `registration_status` | TEXT | Yes | Device registration status. Defaults to `active`; allowed values are `active` and `revoked`. |

## 3. Detailed field explanations

### 3.1 `id`

**Type:** UUID  
**Constraint:** Primary key  
**Default:** `gen_random_uuid()`

This is the permanent database identifier assigned to a registered Zez installation.

Example:

`2f21d16a-ec8e-48f2-a9f5-21c1a7b0d8e3`

The backend generates this ID when registering a device. The frontend stores it securely and uses it when displaying the registered device's identity.

Other tables, such as `calls`, reference this value through a foreign key named `device_id`.

**Important:** This UUID identifies a registered app installation, not a guaranteed permanent hardware identity. Clearing app data or reinstalling the app may require a new registration.

### 3.2 `device_name`

**Type:** TEXT  
**Nullable:** Yes

A readable name for the device, if the operating system makes one available.

Example: `Sayan's Phone`

This field is for display and administration. It must not be used for authentication because names can be changed and may not be unique.

### 3.3 `device_model`

**Type:** TEXT  
**Nullable:** Yes

The model name reported by the device.

Example: `Vivo T3x 5G`

It helps with device diagnostics and compatibility investigations. It does not uniquely identify a physical phone.

### 3.4 `manufacturer`

**Type:** TEXT  
**Nullable:** Yes

The hardware manufacturer reported by Android.

Examples: `vivo`, `Samsung`, `Xiaomi`

This field is descriptive metadata, not a unique identifier.

### 3.5 `brand`

**Type:** TEXT  
**Nullable:** Yes

The brand reported by the operating system.

It may differ from the manufacturer value, depending on the device.

### 3.6 `platform`

**Type:** TEXT  
**Default:** `Android`

Identifies the operating-system platform used by the app.

For the current Zez Android app, the value will normally be `Android`. It can also support future versions on other platforms if Zez expands.

### 3.7 `os_version`

**Type:** TEXT  
**Nullable:** Yes

Stores the operating-system version reported by the app.

Example: `16`

The actual value depends on what the operating system reports. It is useful for investigating permission problems, background restrictions, and device compatibility.

### 3.8 `app_version`

**Type:** TEXT  
**Nullable:** Yes

Stores the version of Zez installed on the device.

Example: `1.2.0`

This can help identify devices running older app versions when debugging synchronization failures.

### 3.9 `sim1_phone_number`

**Type:** TEXT  
**Nullable:** Yes

Stores the phone number associated with SIM slot 1, if Android and the carrier expose it to the application.

Example: `+919876543210`

This field is optional because Android does not reliably expose SIM phone numbers on every device. The SIM may be present even when its number is unavailable.

Do not assume SIM slot 1 is always the default calling SIM or the user's preferred number.

### 3.10 `sim2_phone_number`

**Type:** TEXT  
**Nullable:** Yes

Stores the phone number associated with SIM slot 2, if available.

If the phone has one SIM, or the second number cannot be retrieved, this field remains `NULL`.

### 3.11 `sim1_carrier`

**Type:** TEXT  
**Nullable:** Yes

Stores the available mobile network operator name associated with SIM 1.

Example: `Airtel`

This can be useful when diagnosing network-related problems. The exact value depends on what Android exposes.

### 3.12 `sim2_carrier`

**Type:** TEXT  
**Nullable:** Yes

Stores the available mobile network operator name associated with SIM 2.

If SIM 2 is absent or its operator information is unavailable, the value remains `NULL`.

### 3.13 `sim1_country_iso`

**Type:** TEXT  
**Nullable:** Yes

Stores a country code in ISO format, when available.

Examples: `IN` for India and `US` for the United States.

This is a country code, not a mobile country calling code such as `+91`.

### 3.14 `sim2_country_iso`

**Type:** TEXT  
**Nullable:** Yes

Stores the corresponding country ISO code for SIM 2, when available.

It may be different from SIM 1 if the phone has SIMs associated with different countries.

### 3.15 `primary_phone_number`

**Type:** TEXT  
**Nullable:** Yes

Stores the phone number Zez chooses to treat as the preferred number for display or contact purposes.

Under the proposed policy:

1. Use SIM 1's number if it is available and the user accepts that choice.
2. Otherwise, optionally use SIM 2's number if the user chooses it.
3. If neither number is available, keep the field `NULL`.

This is a preference, not a unique identifier.

Two devices may legitimately have the same number, and a number may be reassigned to a different subscriber. Do not use this field as the device's primary key or authentication credential.

### 3.16 `token_hash`

**Type:** TEXT  
**Constraint:** Unique and NOT NULL

Stores the SHA-256 hash of the secret token issued to the registered device.

The app receives the original token once and stores it in secure device storage. For authenticated requests, it sends that token in an HTTP `Authorization: Bearer` header.

The backend hashes the presented token and looks up the matching `token_hash`.

The original token must not be stored in the database or printed in application logs. If a token is revoked, the backend should reject future requests using it.

**Security note:** A plain SHA-256 hash is appropriate for a randomly generated, high-entropy token. The token should be generated using a cryptographically secure random-number generator.

### 3.17 `registration_status`

**Type:** TEXT  
**Default:** `active`

Indicates whether the registered device is allowed to authenticate.

Allowed values:

- `active`: The device is permitted to authenticate, assuming its token is valid.
- `revoked`: The device must not be allowed to authenticate.

The database check constraint prevents other status values from being inserted.

The backend authentication middleware must explicitly check this field; storing the status alone does not enforce access control.

### 3.18 `created_at`

**Type:** TIMESTAMPTZ  
**Default:** Current database time

Records when the device was registered.

The timestamp includes time-zone information and is useful for auditing, debugging, and determining when an installation first registered.

### 3.19 `last_seen_at`

**Type:** TIMESTAMPTZ  
**Default:** Current database time

Records the last successful authenticated contact from the device.

The backend should update it after successful authentication or a successful API request. It should not rely solely on a value supplied by the mobile app.

This field is useful for identifying devices that have not synchronized recently.

### 3.20 `updated_at`

**Type:** TIMESTAMPTZ  
**Default:** Current database time

Intended to record when device metadata was last updated.

For example, it could change when Zez updates the stored device model information or the user's preferred phone number.

PostgreSQL does not automatically update this field on every `UPDATE` just because it has a default. The backend must update it explicitly, or you must create a database trigger.

## 4. Indexes

The table definition creates these indexes:

| Index | Purpose |
|---|---|
| Primary-key index on `id` | Quickly identifies a device by UUID and enforces uniqueness. |
| Unique index on `token_hash` | Finds a device by its token hash and prevents token-hash duplicates. |
| `devices_primary_phone_number_idx` | Helps queries that search by the preferred phone number. |
| `devices_created_at_idx` | Helps sort or filter devices by registration time. |

The phone-number index does not enforce uniqueness. This is intentional because a phone number is not a reliable permanent device identity.

## 5. How the tables relate

The intended relationship is:

`devices (1) ───── (many) calls`

The `calls` table should contain a `device_id` column referencing `devices.id`.

For example:

| Device | Device UUID | Number of associated calls |
|---|---|---:|
| Mobile 1 | UUID-A | 120 |
| Mobile 2 | UUID-B | 85 |
| Mobile 3, no SIM | UUID-C | 32 |

All 237 calls can be stored in the same `calls` table. Each row belongs to the installation identified by its `device_id`.

When adding contacts, use a separate `contacts` table with its own `device_id` foreign key. Do not create a separate table for each phone.

## 6. Important implementation notes

1. **Do not depend on SIM information for registration.** The device should register successfully even when all SIM-related fields are `NULL`.
2. **Treat phone numbers as optional personal information.** Collect and store them only with a clear user-facing purpose and appropriate consent.
3. **Keep device identity separate from SIM identity.** A SIM replacement should not automatically create a new device.
4. **Protect all device-owned data.** The backend must derive the owner from the authenticated token rather than trusting a client-supplied `device_id`.
5. **Handle metadata updates carefully.** A missing value in a later request should not accidentally erase a previously known value unless the user explicitly removes it.
6. **Plan token recovery.** If the app loses its token, use an explicit re-registration or recovery policy. Do not let anyone take over a device merely by knowing its UUID or phone number.
7. **Preserve existing data.** Before dropping or recreating this table, verify foreign keys and back up the database.

## 7. Registration lifecycle

1. The app starts and checks SecureStore for an existing device token.
2. If valid credentials exist, the app reuses them.
3. If no credentials exist, the app requests registration.
4. The backend creates a UUID and a cryptographically random token.
5. The backend stores the token hash and any available device metadata.
6. The app securely stores the returned UUID and token.
7. Subsequent call-log and contact uploads authenticate using that token.
8. The backend attaches the authenticated device's UUID to every stored record.

This design supports single-SIM phones, dual-SIM phones, and devices without SIM cards while keeping data ownership consistent.
